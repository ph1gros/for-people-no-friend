# V1.2 角色资料库与检索边界

V1.2 第一批搭建角色资料底座，并移除已经没有实际用途的跨角色切换 UI 与 IPC。目标是让“这条角色设定从哪里来、为什么本轮会被取出”可以检查，同时让 Live2D 与 WebP 两条路线从入口开始各管各的，而不是先搬来一座数据库动物园。

## 现状与问题

V1.1 的 `CharacterLore` 适合一张轻量角色卡，但来源主要挂在整张卡上。身份、背景、关系和说话方式无法分别表达证据范围；情境例子虽然有 `sourceId`，仍缺少统一的字段路径、证据性质和检索命中理由。

当前还有两套互不相同的检索：情境例子按少量中文意图词打分，作品词库按术语或别名精确匹配。它们都能安全工作，但还没有统一的角色命名空间约束、上下文字符预算和可选语义索引回退协议。

Live2D 的状态、动作、表情和跟踪通道已经彼此分开。双版本表现能力的统一验收以及动态 WebP 的标签判定延期到 V1.3；WebP 播放实现仍只属于 `gif-version`，V1.2 不在 `main` 重写表现层。

## 双版本角色生成边界

- `main` 以凯尔希作为 Live2D 完整示例，不列出或激活伊蕾娜；`gif-version` 以伊蕾娜作为 WebP 完整示例，不列出或激活凯尔希。
- 两个版本都保留公开资料检索、角色候选消歧、生成带字段来源的草稿，以及用户确认后保存的能力。
- 角色资料生成不等于跨格式生成表现素材。Live2D 模型和 WebP 图片分别经过本版本的清单、路径、尺寸与授权检查。
- 当前版本一次只维护一个正在使用的角色资料，因此不需要“列出角色”和“激活角色”IPC；以后若增加自建角色库，应设计成本版本内部的管理功能，不能复用跨版本切换。
- 对话、长期记忆和私人配置不进入示例包，也不随角色草稿导出。

## 不同的体验预算

共享 schema 不代表共享默认负担。

### WebP Version：本地小模型优先

- 角色生成默认输出紧凑卡片，保留称呼、核心身份、三至五条性格或说话规则、少量关系与情境例子，不把整份资料每轮塞给模型。
- 关键词检索、最近对话和确定性回退组成基础路径；不要求用户安装 Embedding、向量数据库、Neo4j 或额外服务。
- 本地兼容接口应给出容易理解的默认值和连接检查。角色资料不足时坦率回到泛用角色，不靠超长提示词硬撑效果。
- 长期记忆仍可使用，但首次生成角色和开始聊天不依赖自动提取、复杂画像或关系模型。

### Live2D Version：neuro-like 长期陪伴方向

- 稳定身份、关系、可信长期记忆和本轮情绪线索分层注入；大型模型有更宽预算，但仍只取相关资料，不能把数据库整锅倒进上下文。
- “情感回复”表示根据用户明确表达和当前对话选择合适的语气与表现，不宣称角色真实拥有情感，也不把一次情绪推断永久写进用户画像。
- 模型输出的结构化情绪只用于选择已经授权的 Live2D 表情和动作；无法解析、动作缺失或可选资料检索失败时，回到中性回复和基础待机。
- 重点评测跨轮事实一致性、关系语气连续性、低落或愤怒场景的边界，以及文字、表情和动作是否互相打架。

根据用户指定的 [my-neuro](https://github.com/morettt/my-neuro) 仓库，`neuro-like` 指的是受 Neuro-sama 启发的长期 AI 角色方向。该项目已经公开说明长期记忆、核心记忆、用户画像候选、AI 日志和时间信息的协作方式；其 README 则把长期情绪状态列为继续开发的核心目标，不能把目标误写成已经成熟的现成实现。

本项目从这个方向中采用几类可以分别检查和安全失效的信号：

1. 角色资料决定“她是谁、通常怎样表达”；
2. 已确认长期记忆提供与用户有关的稳定事实，不包含未经确认的情绪猜测；
3. 近期对话保留眼前发生了什么，避免旧记忆压过当前语境；
4. 关系状态只由明确、可追溯的互动逐步变化，不因一句话突然跳级；
5. 本轮情绪判断决定回复策略和表现候选，不直接改写长期人格；
6. 表现调度把最终回复映射到 Live2D 表情与动作，失败时独立回退。

上下文组装层只选择本轮相关的小量信号交给大型 LLM，并保留命中原因和字符预算。这样既能形成连续感，也能定位“记错了、情绪过头了，还是动作选错了”。V1.2 已实现可信记忆与本轮情感回复边界；跨会话持续情绪需要单独的数据生命周期、衰减、恢复和用户重置设计，不能偷偷塞进用户长期记忆。V1.2 仍不加入语音、Agent、工具调用、屏幕观察或桌面控制。

## 第一批数据模型

`CharacterKnowledgeBase` 使用版本 1 schema，并固定包含 `characterNamespace`。资料条目按用途拆为：

- `identity`：身份与稳定定位；
- `trait`：性格、价值取向和判断习惯；
- `event`：经历、事件与背景；
- `relationship`：单独的人物关系；
- `scenario`：场景、触发、态度和短表达参考；
- `speech-rule`：称呼、句式、语气与禁止写法；
- `example-line`：少量短句参考。

每条记录都有 `evidence`，其中保存来源 ID、原字段路径和证据性质：

- `direct`：来源直接支持该字段；
- `synthesized`：由来源归纳出的说话方式或情境行为，不冒充逐字原文；
- `legacy-aggregate`：旧角色卡只有整卡来源，尚不能证明具体字段。迁移时诚实标记，不能悄悄升级成字段级实证。

第一批提供旧 `CharacterLore` 的只读适配器，不写回 `character-profiles.live2d.v1.json`。第二批在现有 `deskpet.v1.sqlite` 中加入独立的角色资料表：命名空间、来源、资料记录和字段证据分别保存，使用外键与事务保证完整性。它不复用用户记忆表，也没有把旧角色卡自动写入数据库。

资料库采用整命名空间原子替换，适合以后把“用户确认过的一版角色资料”作为一个版本保存；删除角色资料时会级联硬删除该角色的记录和证据，不影响其他角色、聊天、作品词库或用户记忆。损坏的来源 URL、关键词 JSON 或悬空证据会让可选资料库返回为空，由上层回到旧角色卡，而不是带病注入聊天。

## 检索策略

基础检索始终是本地关键词：

1. 先按 `characterNamespace` 隔离候选；
2. 使用显式关键词、别名和中英文规范化文本打分；
3. 返回命中理由，排序保持确定性；
4. 最多返回 8 条、8,000 字，普通默认是 4 条、2,400 字；
5. 格式化结果明确标注“角色设定，不是用户长期记忆”。

可选语义检索器只能补充候选，不能替代关键词结果，也不能返回当前命名空间之外的记录。接口报错、返回非法分数或索引缺失时，直接使用原来的关键词结果。第一批不安装 Embedding 模型，不连接 Qdrant 或 Neo4j，也不把接口复用到用户长期记忆。

关键词层还保留一小组可审查的中文意图提示，用于把“难过、需要保护、受到辱骂”等用户表达映射到角色资料中的情绪和场景标签。它只提高已有资料条目的召回分数，不自行生成角色事实，也不会把脏话直接写进角色卡。

### Live2D 社区梗检索发散

作品社区词库对 Live2D 主线采用本地、有界且可重复的检索扩展。作品名先解析为词库命名空间，不参与正文打分，因此不会因为两个作品使用相似词汇就跨作品取词。每轮最多使用三条查询：当前消息、从引号或“什么意思/什么梗”句式中提取的短词，以及当前消息与最近四条已完成消息中最近一条不同消息的组合。所有查询分别进行关键词排序，再用 Reciprocal Rank Fusion 合并；完全命中术语或别名始终优先。

首批命中后可以沿正文中明确出现的另一个术语或别名关联，最多两层、总计不超过三条。关联只沿真实词库条目移动，不让模型生成新事实。没有可靠命中时不注入猜测，也不静默联网；模型应说明不确定并询问语境，用户仍可通过现有“同步作品词库”入口明确发起公开资料同步。该路径不新增 IPC、网络权限、Embedding、向量数据库或用户记忆索引。

## 参考项目的取舍

[SillyTavern 角色设计文档](https://docs.sillytavern.app/usage/core-concepts/characterdesign/)把稳定角色描述、场景和示例对话分层；[World Info](https://docs.sillytavern.app/usage/core-concepts/worldinfo/)则按条件激活额外资料。这说明“常驻核心规则 + 按需资料片段”比每轮塞入整张资料库更可控。本项目采用分层与预算思路，不复制其代码、宏系统或任意提示注入能力。

[RoleLLM](https://aclanthology.org/2024.findings-acl.878/)把角色资料构建、情境知识、表达风格与角色评估分开。V1.2 对应地拆分资料种类，并计划使用固定问题检查知识、风格和多轮一致性；不引入其训练数据或微调链路。

## 后续批次的采用门槛

SQLite 仍应是真实正文、来源和版本的唯一持久副本。只有关键词评测确实漏召回，才评估本地 Embedding；只有数据规模证明 SQLite 内嵌索引不够，才比较外部向量数据库；只有多跳关系问题明显改善，才评估 Neo4j。所有辅助索引必须可删除、可重建、可关闭。

## 第一批验收标准

- 旧角色卡可以转成带版本、带命名空间的资料记录；
- 旧整卡来源明确标成 `legacy-aggregate`，情境归纳标成 `synthesized`；
- 关键词检索有稳定排序、命中理由、数量和字符预算；
- 另一角色的记录即使同词命中也不会返回；
- 假语义检索器报错时，结果与纯关键词检索一致；
- 不新增 IPC、外部网络、依赖、密钥路径或用户记忆索引；角色资料只使用现有 SQLite 文件中的独立表；
- 自动测试、类型检查、构建和 Preload 安全冒烟通过。

## 自动体验基线

当前固定评测先检查“资料有没有拿对”，不让另一个模型给回答打玄学分：

- 询问角色身份时命中 `identity`；
- 询问阿米娅时命中凯尔希资料中的对应 `relationship`；
- 询问称呼与语气时命中 `speech-rule`；
- 用户表达失败和难过时命中安慰场景；
- 用户直接辱骂角色时命中愤怒或制止场景，而不是继续保持毫无反应的通用语气。

这组测试不调用真实模型。资料检索已经接入基础聊天，并补充本轮情绪策略、关系连续性、已确认事实稳定性和失败回退检查；模型回复的主观自然度仍留给真人实测。

## 第二批：接入基础聊天

Main Process 在每轮聊天开始时，先按当前角色的记忆命名空间读取 SQLite 角色资料。提示词固定保留一条身份和一条说话规则，再按本轮输入补充至多两条相关资料；没有情境命中时可补入稳定性格。整体仍遵守默认 4 条、2,400 字预算。

SQLite 中没有该角色资料、资料损坏或读取失败时，只在内存中把已经验证过的旧角色卡适配为同一格式；不自动写回数据库，也不阻断聊天。成功生成新资料上下文时不再同时拼入整张旧角色卡，避免同一设定重复或新旧字段互相打架。角色资料检索仍只发生在 Main 内部，没有新增 Renderer 权限、IPC 或网络请求。

用户明确保存修改后的角色资料时，Main 会把该角色资料原子替换进 SQLite；普通聊天和应用启动不会触发写入。资料库同时保存由已验证角色卡生成的版本指纹，聊天只采用与当前角色卡指纹一致的记录。文件保存或 SQLite 更新任一步失败时，旧资料不会被误当成新资料，系统会回退当前角色卡继续聊天。

## 暂缓的真人实测

第一批只删除无效的角色切换控件，不改动 Live2D 调度。后续出现可见资料管理或检索解释界面后，再人工检查：字段来源展开、长文本滚动、不同缩放、本版本自建角色之间的资料隔离，以及模型回复是否真正更像角色。真实 Electron UI 自动化和长时间运行也留到后续批次。
