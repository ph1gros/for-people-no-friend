# V1.9 AstraTTS 音色兼容性研究

原始试验日期：2026-09-08；离线指标补充：2026-09-13。阶段状态见 [V1.9 工作记录](V1_9_IMPLEMENTATION.md)。现有生产语音与资源信任表未改变。

## 版本与来源

复用既有官方 Windows 1.2.2 隔离环境，没有重新下载运行环境或模型。上游 1.2.2 标签与本次查询到的 main 均指向 `7b55843b1772c9e6a1741bd54596dc4e98290c33`。核对了 [转换器](https://github.com/Blackwood416/AstraTTS/blob/7b55843b1772c9e6a1741bd54596dc4e98290c33/tools/converter/v1_converter.py)、[模型加载器](https://github.com/Blackwood416/AstraTTS/blob/7b55843b1772c9e6a1741bd54596dc4e98290c33/AstraTTS.Core/Core/InferenceEngineV1.cs) 与 [流式实现](https://github.com/Blackwood416/AstraTTS/blob/7b55843b1772c9e6a1741bd54596dc4e98290c33/AstraTTS.Core/Core/TtsEngineV1.cs)。代码 MIT 许可不替代音色、参考音频和原始素材的授权。

## 已确认的兼容性问题

现有 Genie 菲比音色包含五个 `_fp32.onnx` 图文件，但 decoder、vits、prompt 的实际外置权重以 FP16 bin 存储。Genie 的 `load_session_with_fp16_conversion` 在内存里展开为 FP32，并按 ONNX 外置张量的 offset／length 注入。

Astra 的加载器寻找 `t2s_encoder.onnx`、`t2s_first_stage_decoder.onnx`、`t2s_stage_decoder.onnx`、`vits.onnx`、`prompt_encoder.onnx`，直接创建 ONNX Runtime 会话，不执行 Genie 的这一段外置权重展开。

实际失败复现：只复制并改图文件名称时，服务启动因缺少 `prompt_encoder_fp32.bin` 等外置文件失败。这说明“都是 ONNX”不足以证明音色包直接通用。

## 已完成的无损适配试验

在原有 Astra 隔离目录中新建菲比试验副本：

1. 原样复制五个图文件并去掉文件名中的 `_fp32`；图文件内容逐字节不变。
2. 将三个 FP16 bin 无损展开为其图文件所引用的 FP32 bin。每项均检查有限值、FP32→FP16 回转数值完全相同，以及所有外置张量范围有效。没有量化、训练、裁剪或修改源文件。
3. 使用原菲比参考音频与参考文本，指定本机 127.0.0.1 独立端口、CPU 四线程、池容量 1，生成受控同文本完整／流式音频。没有扬声器播放。
4. 试验结束后停止本次创建的服务。原有桌宠与生产资源未操作。

这验证的是 **现有 Genie 导出包的存储适配**，不是从原始 ckpt／pth 完成上游转换器全流程。转换器要求 ckpt、pth、ONNX 模板与输出目录；本次没有加载原始 checkpoint，也没有安装 PyTorch。上游转换器存在 `weights_only=False` 回退以及缺失模板时跳过的路径，正式工具不能照搬这些失败处理。

## 本次测量

文本固定为“今天我们来测试实时语音合成的表现。”；同菲比音色、同参考录音、语速 1。

| 模式     | 首批数据 | 全部接收及保存 | 音频长度 |
| -------- | -------: | -------------: | -------: |
| 完整生成 | 3.489 秒 |       3.526 秒 |  4.04 秒 |
| 流式 22  | 0.742 秒 |       2.662 秒 |  4.08 秒 |
| 流式 44  | 1.205 秒 |       2.952 秒 |  4.32 秒 |

完整生成是此次进程的首个合成请求，另外两个是随后请求；四线程配置也不同于旧试验，不能从此表推断严格加速比。首批 HTTP 数据不等于首个有效发声；“全部接收及保存”包含客户端写 WAV 的少量开销。流式边界记录是 HTTP 读操作，不能当成引擎内部埋点。

三份音频的本地 SenseVoice ASR 均为原输入正文。ASR 正确不代表音质、接缝或语气通过。

试听材料在 `.release/astra-stream-trial/feibi-compat-expanded/`：`feibi-full.wav`、`feibi-stream-22.wav`、`feibi-stream-44.wav`。同目录包含 results.json、asr-results.json、隔离日志和 service-stopped.json。适配证据位于 `.release/v1.9-research/astra-compatibility.json` 与 `astra-lossless-expansion.json`；直接改名失败证据保留在 `feibi-compat/`。

## 流式连续性与后续

既有晨星试验中，用户已经确认默认流式更卡；本次菲比适配成功不会推翻这个结论。上游仍会重算更长的声码器波形后直接截取新尾部，并在句尾补 6400 个零采样。重复生成差异、接缝不连续和句间静音须独立评估，不能简单删除所有低音量区间。

下一步需要对本次同音色样本进行听感对照，并对同一组真实语义 token 的不同前缀生成埋点，才能更严格地分离语义采样差异和声码器拼接问题。混读、内存与现有菲比停顿气声处理仍需覆盖。当前不把 Astra 替换为默认引擎，也不发布适配音色。

## 补充：长句与断流恢复

长句首次请求返回 HTTP 500，错误为“流式 T2S 推理失败：3 次重试后仍未达到期望 tokens 数量 (66)”。新进程中重试同一文本成功，首批数据 1.909 秒、总接收及保存 14.755 秒、音频 17.36 秒。这是成功与失败并存的实测，不能判为稳定通过。成功样本本地 ASR 基本覆盖正文，但把输入“声音是否连续”识别为“声音是否联系”，需试听区分发音与识别误差。

另外单独启动隔离服务，在短句首批 HTTP 数据到达后关闭客户端连接，再立即请求“你好，这是一句新的恢复测试。”；后者成功返回 3.92 秒音频，本地 ASR 与输入一致。客户端断开后可再次请求得到验证，服务端是否及时中止旧推理、是否节省计算尚未埋点验证。中止样本只保留完整 Float32 采样，丢弃末尾不足 4 字节的传输片段；此前测试脚本曾因半个采样无法转换 WAV 而退出，这属于测试脚本问题，不是引擎报错。

长句材料在 `.release/astra-stream-trial/feibi-long-cancel/`，断流与恢复材料在 `.release/astra-stream-trial/feibi-cancel-recovery/`。各次自建服务均已在 finally 中终止，并写出 service-stopped.json；Windows 主动 terminate 的退出码为 1，不代表自然正常退出。

## 补充：同文本有效能量起点、静音与边界指标

2026-09-13 对既有菲比完整、stream22、stream44 三份 WAV 与同次 HTTP 到达记录做离线分析，没有重启引擎或重新合成。脚本只依赖 Python 标准库，源 WAV 的 SHA256 在分析前后不变。可从仓库根目录重跑：

```powershell
py -3.12 .release/astra-stream-trial/feibi-metrics-20260913/analyze.py
```

方法采用单声道 PCM16 的 10 ms 帧，连续 3 帧 RMS 达到 0.005（约 -46 dBFS）作为“持续有效能量起点”的代理。这不是语音活动识别，也不保证等同于人耳第一次听见声音。另用 0.002、0.01 两个阈值检查敏感性；完整结果及自检在同目录 `metrics.json`、`RESULT.md`。

| 模式     | 音频内持续有效能量起点 | 足够判定该 30 ms 的数据到达时间 | 假定首批数据后缓冲 250 ms 的起点估计 | 内部低能量段（至少 150 ms） |
| -------- | ---------------------: | ------------------------------: | -----------------------------------: | --------------------------- |
| 完整     |                0.87 秒 |                        3.492 秒 |                             4.609 秒 | 0.44–0.87 秒                |
| stream22 |                0.35 秒 |                        0.742 秒 |                             1.342 秒 | 0.63–0.80 秒                |
| stream44 |                0.39 秒 |                        1.205 秒 |                             1.845 秒 | 0.54–0.76 秒、1.29–1.59 秒  |

时间估计使用既有到达记录模拟顺序消费 PCM，并非本次实际播放测量；完整模式也只作相同假设下的对照，不代表实际 WAV 播放器的启动策略。此 250 ms 缓冲模型下，三份短句的传输欠载时长均为 0。阈值从 0.002 改到 0.01 时，完整样本起点为 0.30–0.87 秒，stream22 为 0.33–0.37 秒，stream44 为 0.35–0.77 秒，说明低能量清辅音、气声等会影响定义，不能只用一个数宣称真实首响改善。

两份流式 WAV 都有恰好 0.20 秒的尾部全零段；完整 WAV 没有至少 100 ms 的全零段。三份样本均未发现至少 100 ms 的内部全零段，但仍存在表中的内部低能量段。低能量不等于故障静音，也不能据此删除气声或自然停顿。

按相邻 HTTP 读取间隔超过 30 ms 归并传输突发，stream22 的候选边界位于音频 0.88、1.76、2.64 秒，stream44 位于 1.76、3.52 秒。最突出的候选是 stream22 的 2.64 秒处：相邻采样跳变为满幅的 0.06497，是周围 ±100 ms 一阶差分第 99 百分位的约 2.53 倍。它值得在后续试听与引擎埋点时重点检查；传输突发不是已确认的引擎 chunk 边界，单次局部跳变也不足以判定可听接缝或归因于拼接算法。

本次补齐了同文本样本的可重跑能量、静音与候选边界指标。真实耳听、相同语义 token 前缀的引擎埋点、混读、内存峰值/回收，以及取消后旧推理是否及时停止仍未补齐；既有“断开后新请求成功”证据继续保留，不能扩大为服务端取消计算已验证。Astra 继续保持研究状态。
