# V1.9 情绪与 ViewerEX 映射研究

核对日期：2026-09-08。本文包含上游对照、设计建议和后续 VTS 十通道表达实现；角色关系的持久演化尚未接入。阶段状态见 [V1.9 工作记录](V1_9_IMPLEMENTATION.md)。

## 已有能力与真正缺口

当前 `src/core/character/character-reply.ts` 使用七个表现标签：neutral、happy、sad、angry、surprised、shy、playful。`context-assembler.ts` 要求每条回复只选择一个标签。

`companion-signals.ts` 并非完全无状态：它识别 support、celebrate、boundary、reassure 四种线索，从最近四条记录中的用户消息形成加权心情延续，当前明确线索优先。它也明确约束单轮夸奖、冲突或情绪不能突然改变关系。但这仍是有限关键词规则和单个心情标签，不是十维连续状态；安慰恐惧目前对应 surprised，不能当作已有独立 fear 通道。

角色资料里的 relationships 是背景与人物关系描述；记忆中的 relationship 索引负责检索关系记录。二者都不应被误称为“信任／依恋随时间演化的关系系统”。当前核对的这些路径没有上游那种慢通道数值状态。

## 上游复核

参考 [emotion-engine 固定版本](https://github.com/fenghua2006/emotion-engine/tree/bc0350c6a3870e359db135a249e5212086d810e7)，代码许可为 MIT。研究副本只保存在本地忽略目录，没有运行上游仪表盘或联网聊天。

- [engine.py](https://github.com/fenghua2006/emotion-engine/blob/bc0350c6a3870e359db135a249e5212086d810e7/engine.py) 的 Channel 与 EmotionalState 实际包含 joy、sadness、anger、fear、disgust、surprise、trust、love、longing、guilt 十项；EmotionalState 的注释仍称八通道，确有文档不同步。
- 七个快速通道与 love／trust 两个慢通道分开；longing 是单独的缺席驱动通道。`wake()` 与 `tick()` 分别处理离线和在线时间。
- `Appraisal` 有目标相关性、有利程度、预期程度、应对能力、外部责任和社会评价六个输入。`appraise()` 将其组合成通道激活，输入质量决定结果质量；它不会凭复杂公式自动理解对话。
- `wake()` 会增长思念、调用慢通道增长，并在长时间不联系后降低信任。思念公式旁的注释写 0.12，实际代码乘 0.4。不能照注释复制系数，也不能默认继承这套离开惩罚。
- `respond_llm()` 包含 DeepSeek 默认值、环境变量取钥及备用服务商路径；仪表盘保存 custom_api_key／角色 api_key，并监听 0.0.0.0。只评估状态计算思路，不移植这些服务、凭据或存储路径。
- 论文支持具体公式与系数的程度未核实，不将其称为科学验证完成的情绪模型。

## 推荐的改动边界

保留现有七个表现标签，新增独立的十通道内部状态。不要把 `CHARACTER_EMOTIONS` 直接替换成十个值：它同时影响模型输出、IPC、语音预设、内嵌 Live2D、ViewerEX、VTube 与历史数据。

建议分成四层：

1. **事件评估**：当前角色、当前有效轮次、事件证据、有限数值与不确定性。先用合成对话验证否定、引用、玩笑、第三人称和用户／角色情绪的区别；无法确定时不强行更新。
2. **状态演化**：角色命名空间内的十维向量与更新时间；快情绪回落与慢关系分开。爱与思念是否启用由角色设定决定。默认不因用户离开而扣信任，也不随聊天次数自动加爱。
3. **表达投影**：保留多个激活通道，但选择当前有资源支持的表现。joy→happy、sadness→sad、anger→angry、surprise→surprised 可作为基础候选；fear、disgust、guilt 等没有准确现有标签时回退 neutral 或经用户绑定的动作，不硬套成 surprised／angry。trust、love、longing 不默认等同害羞或调情。
4. **显示端适配**：投影结果继续走现有表现端口。为防表情抖动，投影可采用最短保持时间和切换差值，但阈值需要样本评测，不将任意常数当作角色心理规律。

状态必须按角色隔离；取消或失败轮次不重复更新；同一事件具备去重标识；重启只结算一次；时间倒退与极长离线必须有边界；删除角色应同时清除该状态。这些是正式实现前的回归契约。

## ViewerEX 能直接复用什么

本项目已经有完整的基础映射：

- `viewerex-mapping-draft.ts` 解析与格式化 `语义=标识`。
- `viewerex-ipc.ts` 重验七种情绪、0–4095 的表情 ID 与安全的 group／group:motion。
- `viewerex-protocol.ts` 把表情转换为 13300，把状态／动作转换为 type=0 的 13200。
- `viewerex-service.ts` 管理本机连接与失败回退；无需重新造客户端。

再次核对 [官方 ExAPI 列表](https://live2d.pavostudio.com/doc/zh-cn/exapi/api-list/) 和 [官方 ExAPI 仓库](https://github.com/pavostudio/ExAPI)：有设置表情、下一表情、清除表情、触发动作等操作，但当前公开列表没有枚举模型动作／表情的查询。表情数字 ID 是具体模型的定义，不存在在这些官方资料中确认过的通用十情绪编号表。

[官方模型 JSON 示例](https://live2d.pavostudio.com/doc/en-us/live2d/model-json-example/)提供 expressions 与 motions 结构，可以作为用户自有、获授权明文模型配置的候选清单来源。不能从文件名猜定情绪，更不能把 API 文档示例的 expId=1 当成“开心”。公开搜索到的 LPK 下载／解包工具不作为映射方案，不读取或解包用户 Steam 管理的模型。

现有协议传输可以复用，但现有映射不能直接作为表达效果合格的方案。七标签仅应保留为旧端兼容回退；模型明确支持的 fear／guilt 等表达，不宜先强制压成七类而丢失区别。无需为十通道立刻要求十套资产。

### 修订后的实施优先级

1. **模型能力和预览优先**：每个模型建立已确认的表情／动作清单，显示名称与用途；未知名称仅为候选。ViewerEX 缺乏枚举接口时，使用作者提供的明文说明或逐项预览绑定，不能靠通用编号表补齐。
2. **表达不再只有一个数字**：一种情绪可配置多个候选动作／表情，区分强弱与语境；眼泪、红晕等面部表达与点头、低头等动作分别管理。ViewerEX 只能触发已制作的资源，不能承诺它具有内嵌渲染器那样的连续参数混合能力。
3. **补完整生命周期**：明确开始、保持、恢复、取消、切模型后的行为；处理状态动作与回复动作的优先级。为未映射情绪制定可解释的回退，不静默沿用上一张脸。
4. **十通道稍后接入**：把模型能力传给表达选择层，允许确有资源支持的细分表达直接选择；七标签保留兼容用途。十维内部状态不能解决错误资源绑定，也不应只取最大值便认定表现自然。

实际验收采用固定对话序列，例如“庆祝 → 严肃讨论 → 安慰 → 回到待机”，分别核对选择、时机、恢复和模型资源。此处是设计修订与协议复现结果，尚未实施新的表达调度器或声称观感改善。

## VTS 十通道表达实现

用户随后明确要求执行 VTS 独立推进路线。当前实现从模型回复中的可选 `emotionChannels`，经完成事件、表现接口和 Main IPC 校验，到 VTS 参数注入；无需更换显示后端或增加依赖。

- 十个字段为 joy、sadness、anger、fear、disgust、surprise、trust、love、longing、guilt；每项必须是有限的 0–1 数值，缺省为 0。模型返回非法表达元数据时保留正常正文和旧情绪；Main 接收非法 IPC 时严格拒绝。
- 这是**本次回复的十维表达强度**，只随成功完成事件发送，不进入历史数据库或关系记忆。不是 emotion-engine 的 Appraisal／tick／wake 状态系统，也没有离线增长、关系积分或跨会话累积。
- 七个快速表达通道混合到嘴角、眉毛、张嘴及左右眼；强度总和小于 1 时保留弱表达，大于 1 时归一化。fear、disgust、guilt 有独立初始参数，不先变成旧标签。数值是艺术预设，未声称心理学验证或所有模型观感一致。
- trust、love、longing 只小幅软化已有表达，三者单独出现时仍为平静，不自动制造红晕、眨眼或笑脸。它们不是持久关系分数。
- 若只有一种基础面部情绪、旧标签与之对应且模型有已确认文件，则沿用该文件；文件模式不能保证连续强度。混合或细分情绪走参数模式，只解除本程序持有的活动表情，不清理用户无关配饰。
- 渐变从当前实际混合值继续，修复旧实现快速切换时沿用旧起点的问题。8 秒待机恢复也覆盖“旧标签 neutral、十通道非零”的情况。停止连接会销毁该参数状态；模型切换沿用既有会话重建逻辑。
- 旧回复、ViewerEX 及语音继续使用七标签；内嵌模型后续接入见下节。设置里的原有表情预览仍是七标签；尚未新增十维调参面板。

自动验证覆盖混合回复解析和 Main 边界、非法数值软降级／拒绝、强弱混合、关系通道单独输入保持平静、渐变中途切换、待机释放、真实本机 WebSocket 的 VTS 请求，以及聊天完成事件。真实模型参数绑定、表现区别和观感仍待目视验收。

## ViewerEX 表达逻辑改进

用户继续要求落实 ViewerEX 改进后，新增以下行为：

- 设置支持 `emotionMotions`，每种旧情绪最多 8 个不同安全动作组／动作标识。输入示例 `happy=tap:smile | tap:nod`，示例不是模型自带编号或动作的保证。设置保留原版本兼容，旧文件缺少该字段仍可读取。
- 同次输入只选择一个动作：已映射的显式动作优先，其次情绪动作，最后状态动作。情绪动作候选可轮换；表情仍可与所选动作一同发送。
- neutral 有已配置编号时使用该编号；否则只有本程序曾发送过表情时才发 13302。切到未映射情绪也释放本程序持有的旧表情，避免无声沿用上一张脸。
- 回复后进入 idle 时先留 1.5 秒动作窗口，8 秒后发送 neutral 恢复；新状态／新回复取消旧计时器，切显示模式及窗口卸载清理计时器。ExAPI 无动作结束事件，因此 1.5 秒是初始时长，不是实际动作播放完成证明，长动作仍可能需要后续调校。
- 设置中的预览改为选择具体情绪，只发该情绪，重复点击可查看候选。可以选择“平静／恢复”结束。修改同一连接的映射不再断开连接并丢失本程序持有的表情记录；关闭或更换目标时尽力在旧目标释放后断开。

ExAPI 的清除表情是模型级操作，没有 VTS 那样的单文件所有权控制。这里只记录“本程序是否发送过表情”；无法检测用户随后在 ViewerEX 手工改变的表情。使用自动恢复期间若同时手动叠加表情，清除仍可能影响它们。断线后丢弃本程序记录，不在重新连接时盲目清除。

本次未增加模型资源扫描、表情语义自动识别、十通道专用 ViewerEX 槽位或加密资源读取。新增配置、协议选择、轮换、恢复计时与旧设置兼容通过自动测试；具体模型效果待实际预览。

## 原生 Live2D 十通道表达

用户要求后，将同一份可选 emotionChannels 贯通 AutonomousActivityPresentation、Live2DPerformanceController 与 Pixi 驱动。单一基础情绪已有模型 Expression 时保留原文件；混合与新增细分表达进入模型参数层，缺乏受支持参数的模型回退旧标签路径。

原生参数层使用 Cubism 的 ParamMouthForm、ParamBrowLY／RY、ParamEyeLOpen／ROpen，依据实际参数范围归一化并限幅。它不使用 VTS 的 MouthSmile／Brows 输入名，也不创建模型不存在的虚拟参数。模型清单中的固定参数优先，口型参数跳过；张嘴参数完全留给音频和 Motion，以兼容引擎自己的动作音频。眼睛在本帧眨眼值上缩放，已闭合的眼睛不会被情绪强行打开。

更新顺序为引擎 Motion／Expression／物理 → 既有眨眼补偿 → 情绪混合 → 固定参数 → 本程序口型 → model.update。已核对安装的 untitled-pixi-live2d-engine 1.3.5 在 beforeModelUpdate 之前保存动画参数，在 model.update 之后 loadParameters，因此本层写入不会累积到下一帧。一次性动作播放期间暂停本层，动作完成或驱动超时后恢复最新目标。

渐变为 320 毫秒，从当前混合向量继续；进入 idle 后 8 秒释放通道，销毁模型时清理计时器。trust／love／longing 与 VTS 一样只软化已有面部表达，不能单独制造依恋表情，不进入持久关系系统。标准参数名也不保证所有模型的艺术含义完全一致，自定义参数模型需要另外的显式绑定。

自动测试验证模型范围、快速切换连续性、眨眼闭合、口型／固定参数保护、动作暂停、无参数回退、包装层透传、旧表情优先与待机释放。尚未启动当前桌宠做真人目视验收，也未增加十维调参界面。
